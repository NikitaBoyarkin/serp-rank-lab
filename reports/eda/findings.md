# EDA Findings — serp-rank-lab (SERP ranking & monetisation)

**Дата:** 2026-10-13
**Полный отчёт:** `reports/eda/eda-serp-rank-2026-10-13.md`

## Датасет вкратце

Обработанный слой `serp-rank-lab` содержит 6 parquet-таблиц; первичная —
`serp_offers.parquet`: 120,136 строк, одна строка = показ предложения (`search_id` ×
`position` × `partner`), 12,000 поисков, 4,570 пользователей. Метрика — `commission`
(94.57% нулей, skew 7.79). `data/raw/` пуст, поэтому EDA описывает только обработанный
слой. Качество данных в целом — **приемлемое**: структура чистая и логика цепочки
click→redirect→book не нарушена, но есть семантические ловушки (CPA/CPC) и неоднозначный
grain заказов.

## Топ проблем качества

### Проблема 1: `commission` смешивает CPA- и CPC-экономику
- **Что:** `commission` = CPA-комиссия на брони **или** CPC-плата за клик, иначе 0
  (`src/serp_sim.py:497-499`). 2,361 показ имеет комиссию без брони — все CPC.
- **Влияние:** `sum(commission)` ≠ «выручка за бронь». Разница 86,022 (0.58%) между полной
  суммой и booked-only (`sql/03_funnel.sql:25`). Дашборды могут показывать завышенную
  «выручку».
- **Действие:** для «выручки за бронь» использовать `booked_commission`; `commission`
  помечать как «CPA+CPC».
- **Владелец:** аналитик / дата-инженер.

### Проблема 2: `order_id` не уникален (grain заказов неоднозначен)
- **Что:** `data/processed/orders.parquet` — 8,966 строк, но 8,803 значения `order_id` →
  163 дубля (1.8%); 4 полных дубля строки. FAIL по порогу «дубли по ключу > 0%».
- **Влияние:** агрегаты по заказам (число, средний чек) могут быть смещены, если один
  заказ представлен несколькими строками.
- **Действие:** уточнить grain у дата-команды; до этого фиксировать оговорку в метриках.
- **Владелец:** дата-инженер / бизнес-заказчик.

### Проблема 3: у первичной таблицы нет настоящей оси времени
- **Что:** `serp_offers.booking_month` — номер месяца **1–8** без года (спека ожидала 1–12).
- **Влияние:** тренд и аномалии по `serp_offers` не считаются; доступна только сезонность.
- **Действие:** принять как ограничение модели; динамику читать по измеренной ветке `orders`
  (`order_date`, 11 недель).
- **Владелец:** аналитик.

### Проблема 4: `expected_revenue` не является прокси выручки
- **Что:** корреляция `expected_revenue ~ commission` = **0.248**, тогда как с `click_prob`
  = 0.849. Величина доминируется вероятностью клика, а не комиссией.
- **Влияние:** ранжирование/оценка по `expected_revenue` сместит выбор в сторону кликабельных,
  а не доходных предложений.
- **Действие:** не использовать `expected_revenue` как прокси выручки; для денег — `commission`
  (с оговоркой CPA/CPC) или `booked_commission`.
- **Владелец:** аналитик.

### Проблема 5: выбросы в `order_price` не классифицированы до конца
- **Что:** skew 51.6, max 10,435,139 при медиане 15,377; IQR-выбросов 8.8%.
- **Влияние:** среднее по `order_price` бессмысленно; единичный крупный заказ тянет агрегаты.
- **Действие:** докладывать медиану/p95; пометить крайние значения для ручного разбора.
- **Владелец:** аналитик.

## Что в порядке

- `serp_offers` — **0 полных дублей**, ключ (`search_id`, `position`) уникален.
- Логическая цепочка `clicked → redirected → booked` без нарушений (booked ⇒ clicked).
- Диапазоны валидны: `commission >= 0`, `relevance`/`examine_prob`/`click_prob` в [0,1],
  `position` 1–15, даты без будущего.
- Reconciliation: `partner_quality` и `revenue_per_search` совпадают с агрегатом `serp_offers`
  **точно** (дельта 0); `funnel_by_position.bookings` совпадает по всем позициям.
- A/B-сплит без SRM: sessions 49.75% / 50.25%, events 50.2% / 49.8%.
- README-числа воспроизводятся: +38% → 37.72%, +19.3% → 19.28%, 47.3% → 47.35%,
  99.3% → 99.28%, 0.163/0.629 → 0.16304/0.6287.
