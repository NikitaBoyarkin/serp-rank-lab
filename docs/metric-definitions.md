# Определения метрик и правило остановки

Один термин — одно значение. Формулы даны с источником `file:line`; если формула меняется,
меняется этот файл. Числа — из `reports/headline.json` и `reports/experiment.json`.

## Денежные метрики

### revenue (она же `commission`)

Выручка сайта на `serp_offers` — **только комиссия партнёра**, реализованная на строке
показа: CPA-комиссия на брони, CPC-плата на клике, 0 в остальных случаях.

```
commission = commission_rate × price                      # CPA, если booked
commission = cpc                                          # CPC, если clicked
commission = 0                                            # иначе
sum(commission) по SERP = выручка сайта за этот поиск
```

- Определение: `src/serp_sim.py:40-42`
- Начисление: `src/serp_sim.py:479-501`
- Контрактная ставка на «клик с переходом»: `src/serp_sim.py:261-281`
- Агрегат на поиск: `src/ranking_eval.py:345`

**Не равно** цене билета и не равно прибыли сайта: это верхняя строка до затрат на трафик.

### expected_revenue

Детерминированная модель выручки предложения при текущем порядке: вероятность клика,
умноженная на выручку при клике. **Не наблюдается** — это эталон симулятора, поэтому
оракулы, читающие `expected_revenue`, в headline не попадают.

```
expected_revenue = P(click) × revenue_if_engaged
P(click)         = examine_prob(k) × relevance
```

- `src/serp_sim.py:521`
- `revenue_if_engaged`: `src/serp_sim.py:261-281`

### order_value

Реальная цена заказа в измеренном слое `orders`. **Это не выручка сайта**: цена
бронирования пользователя, не связанная с комиссией партнёра.

```
order_value = orders.order_price
```

- Колонка: `sql/01_normalize.sql:77`
- Загрузка: `src/data_ingest.py:147-152`

### service_profit

Прибыль на одной платной доп. услуге внутри строки `orders`. Размечена только у **20.4%**
строк (1,830 из 8,966); среди размеченных медиана **399.2 ₽**. Остальные 79.6% —
**не нули, а отсутствие метки**, поэтому чтение прибыли по всей таблице описывает только
размеченные услуги.

```
service_profit = orders.service_profit
service_margin = service_profit / NULLIF(service_price, 0)
```

- `sql/01_normalize.sql:80-81`
- Сводка: `src/business.py:76-82`

### revenue per search

Основная метрика ранжирования и раскатки: отношение сумм, а не среднее отношений.

```
revenue_per_search = sum(commission) / count(distinct search_id)
```

- Политика (математическое ожидание под новым порядком): `src/ranking_eval.py:345`
- Логированная (фактическая): `src/ranking_eval.py:805`
- Ratio-тест: `src/experiment.py` → `stats.delta_method_test`, кластер `user_id`

## Guardrail-набор

Четыре guardrail'а, у каждого — направление, в котором изменение вредно. Все считаются
на уровне поиска, затем агрегируются по пользователю (кластер SE = `user_id`).

| Guardrail | Формула | Вредная сторона | Источник |
|---|---|---|---|
| CTR | `clicks / offers` | вниз | `src/experiment.py:422-445` |
| Конверсия в бронь | `searches with ≥1 booking / searches` | вниз | там же |
| Средняя цена в топ-5 | `mean(price)` по слотам 1–5, среднее по поискам | вверх | там же |
| Доля офферов дороже медианы | `offers_above_median / offers` | вверх | там же |

Сборка читаута: `src/experiment.py:490-502`.
Порог: `GUARDRAIL_MAX_REL_CHANGE = 0.10` (`src/experiment.py:80`).

## Правило остановки

> **Не катим, если guardrail хуже чем на 10% в свою вредную сторону И разница значима
> после поправки Holm на семейство из 5 проверок (primary + 4 guardrail).** Пробой
> блокирует раскатку независимо от выручки. Сырое p и вердикт по нему остаются в
> `multiplicity` и `decision.verdict_raw`.

- Реализация: `src/experiment.py:448-488` (`_guardrail`), `:510-556`
  (`multiplicity_readout`), `:571-608` (вердикт)
- Факт: пробой `ctr` (−13.06%, p = 7e-6) и `booking_conversion` (−16.05%, p = 0.0088)
  → `do_not_ship`
- Граница CI сообщается отдельно: у CTR интервал [−18.75%; −7.36%], и его **ближняя
  к нулю** граница −7.36% порог 10% не переходит. То есть порог перейдён **точечной
  оценкой**, а не всем интервалом. Это записано в отчёте, чтобы правило не выглядело
  строже, чем оно есть.

## Чего guardrail'ом быть не может

**Refund rate не может быть guardrail'ом: нет join.** `orders` — остров: в нём нет
`user_id`, нет внешнего ключа к кликстриму и нет пересечения по времени с `events`.
Связать возврат с конкретным ранжированием невозможно, поэтому refund rate остаётся
описательной метрикой измеренного слоя (`src/plots.py:171-179`), а не гейтом раскатки.

**163 дубликата `order_id`.** `orders` — 8 966 строк и 8 803 уникальных заказа: строка
это заказ × услуга. Любая метрика «на заказ» обязана дедуплицировать по `order_id`,
иначе заказы с несколькими услугами считаются несколько раз.
